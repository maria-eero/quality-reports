CORE-33235 landed against MACsec Port Security — the interface with 12 contract tests and 3 integration tests merged on each platform. The tests passed. The bug shipped.
This section is the argument against over-claiming for the approach that shipped, and it is the reason the implementation guide presents two approaches rather than one.
Why the shipped tests missed it
What the shipped tests assertWhat CORE-33235 actually is
The client decodes a Port Security payload correctly — field types, malformed-input tolerance, enum handlingThe client decoded correctly, then derived the wrong thing from correct data
Golden fixtures represent payload shapes captured from the APIThe fixtures had no case for a port whose pair-facing port is enabled while it is not
Integration tests assert the ViewModel emits the state the API reportedThe app renders enabled for the WAN port whenever the pair-facing port is enabled — a client-side derivation the API never asked for
Three honest conclusions

1 — A decode-boundary test does not cover a derivation

The fix is a contract test on the predicate: for each port, enabled must equal the node-reported state for that port. Not a broader framework. This is cheap and should be added to both platforms now.

2 — Golden fixtures only cover shapes someone thought to record

The pair-facing-port case existed in the hardware — reproducible on Novo-Crane and Novo-Snowbird, not on Hornbill-Crane — and not in the fixture set. Fixture coverage is a function of imagination, which is the same weakness as mocks, just shared between platforms instead of per-developer.

3 — This is where consumer-driven contracts earn their cost

A Pact-style contract makes the consumer's expectation an artifact the provider verifies. Cloud already reported this port as not MACsec-capable — the correct data existed on the cloud side. A provider-verified contract declaring "the client renders enabled only for ports reported capable and enabled" would have failed in cloud CI, where the truth already lived.

What this does not mean. The shipped approach is not wrong and does not need replacing. It caught a real class of bug at zero infrastructure cost and it gates every PR today. What CORE-33235 shows is the boundary of what a client-side fixture test can see: it validates the client against a recording, and a recording cannot disagree with you. Provider verification is what makes the other side of the boundary answerable.

The design decision that mattered

An earlier iteration gated these behind an opt-in test:contract job with a diff-scoped selection script and a run-contract-tests label. After discussing it with an Android engineer that was dropped in favour of the standard unit scope: the tests are fast, deterministic and dependency-free, so there is no reason to treat them differently from any other unit test. The merged Android PR touches four files, all under app/src/test/, and no CI config.

Phase 3 — integration tests (4–8 weeks)

Cross-service state-transition tests: the invariant that a write is visible on the read path, and that a reported status matches physical reality. Start with the WAN active invariant (CORE-32917, 33148, 33341), setup-success honesty (CORE-33057, 33304), factory→cloud node sync (CORE-33309, 32469) and activation idempotency (CORE-33055). Run against staging or faked API clients, in existing suites, on every PR. The Android PortDetailViewModel INT pattern is directly reusable for the client half; the cloud half needs the provider-side work in the guide.
